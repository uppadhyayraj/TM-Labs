# Act 1 — The Quick Win
### Democratizing API Testing with AI

> **Goal:** Generate a complete API test suite for MyBasket — from zero —  
> using AI alone. No structure. No patterns. Just the prompt and the MCP server.

---

## What you are doing in this act

You will use four MCP skills to plan, execute, and generate tests for a six-service  
microservices application — without writing a single line of test code manually.

By the end of this act you will have:
- A structured test plan with 26+ scenarios
- A live executed happy-path journey with chained JWT tokens
- A generated Playwright TypeScript test suite
- An interactive HTML execution report

---

## Before you start

Confirm your project looks exactly like this:

```
your-project/
├── .vscode/
│   └── mcp.json
├── playwright.config.ts
└── tests/
```

> **No `src/` folder. No page objects. No existing tests.**  
> If you have anything else, remove it before continuing.

Confirm MyBasket is running:

```bash
curl http://localhost:3000/health
# Expected: { "status": "ok" }
```

---

## Step 1 — Health check all services

Open Copilot Chat in VS Code and run:

```
/test-execution Run a health check against all six MyBasket services.
Base URL: http://localhost:3000
```

**What to look for:**
- Six services respond
- All return HTTP `200`
- Response includes `{ "status": "ok" }` for each

> If any service returns something other than 200, let the presenter know  
> before continuing.

---

## Step 2 — Generate the test plan

```
/api-planning Read the OpenAPI schema at http://localhost:3000/api-docs.json
and generate a structured test plan for the full user journey
and realistic edge cases. Include context-aware sample data.
```

**What to look for:**
- A `test-plan.md` file is saved in your project
- The plan covers the full user journey: register → login → browse → cart → order → history
- Edge cases are included: duplicate registration, wrong password, missing auth, empty cart
- Sample data is generated: names, emails, addresses, payment methods

**How many scenarios did you get?** Note the number — compare with your neighbours.

---

## Step 3 — Execute the happy path

```
/test-execution Use session ID "act1-demo". Run the full happy-path
user journey: register → login → browse products → add to cart →
place order → verify order history.
Chain JWT tokens and resource IDs automatically between steps.
```

**Watch the chain execute. Note what happens at each step:**

| Step | Endpoint | What gets extracted |
|---|---|---|
| Register | `POST /api/users/register` | `user_id` |
| Login | `POST /api/users/login` | `jwt_token` |
| Browse | `GET /api/products` | `product_id` |
| Add to cart | `POST /api/cart/add` | — |
| View cart | `GET /api/cart` | — |
| Place order | `POST /api/orders` | `order_id` |
| Order history | `GET /api/orders/history` | — |

**What to look for:**
- The JWT token from login is automatically forwarded to every subsequent request
- You never typed the token — the MCP server chained it
- All seven steps pass

---

## Step 4 — Generate the Playwright tests

```
/test-generation Convert the test plan into runnable Playwright
TypeScript tests. Place them in the correct directory.
```

Wait for the files to appear.

**Now — before you look at your neighbour's screen — note down your answers:**

1. What are your test files named?
2. How is the base URL handled in your tests? (hardcoded? in config? in a variable?)
3. How is the JWT token handled? (hardcoded? extracted? stored in a fixture?)
4. How many files were generated?
5. Is there any shared code between test files, or is each file standalone?

---

## Step 5 — View the HTML report

```
/test-execution Generate the HTML report for session "act1-demo".
Save to ./output/act1-report.html
```

Open `output/act1-report.html` in your browser.

**What to look for:**
- Every request listed with full URL, method, status code
- Response body visible for each step
- Timing metrics per request
- All steps showing as passed
